# Совместное редактирование: проект моста `@inkbrick/collab`

Проект, ещё не реализован. Описывает, как редактор Inkbrick подключается к CRDT ([Yjs](https://github.com/yjs/yjs)), чтобы
несколько человек правили один документ одновременно. Транспорт и сервер сюда не входят: мост работает с любым способом доставки
обновлений. Числа и имена API ниже это предложение для прототипа, а не обещание.

## Принципы

1. **Ядро не знает о CRDT.** `@inkbrick/document`, `store`, `engine`, `react` остаются пригодными без Yjs. Мост живёт в новом пакете
   `packages/collab`, Yjs у него в `peerDependencies`.
2. **Источник правды это `Y.Doc`.** Модель Inkbrick (`Document` в `DocumentStore`) его проекция. Сохраняется и передаётся только
   состояние Yjs; JSON-снимок получается из него.
3. **Команды не переписываются.** Локальная правка идёт как сейчас: команда → транзакция хранилища. Мост после коммита переносит
   результат в `Y.Doc`.
4. **Чужие правки приходят одним способом.** Мост строит проекцию `Y.Doc`, сравнивает с хранилищем и применяет разницу. Тот же код
   работает для правки соавтора, для undo и для полного восстановления, если что-то разошлось.

```
команда ─▶ store.transact ─▶ subscribeChanges ─▶ мост: разница блока с Y.Doc ─▶ Y.Doc ─▶ обновление наружу
                                                                                  ▲
экран ◀─ store (origin: remote) ◀─ мост: проекция Y.Doc, разница с хранилищем ◀───┴── обновление снаружи, undo
```

## Формат документа в Yjs (`inkbrick-yjs`, версия 1)

```
Y.Doc
├ meta:   Y.Map   { format: 1, rootId, schemaVersions: { flavour: n } }
└ blocks: Y.Map   blockId →
          Y.Map   { flavour: string,
                    place:   { p: parentId, k: ключ порядка },   // одно значение, пишется целиком
                    props:   Y.Map (ключ → JSON-значение),
                    text:    Y.Text }                            // есть у каждого блока, даже без текста
```

| Поле модели                | В Yjs                                                                                                                 | Почему                                                                                                                        |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `children`, `parentId`     | не хранятся; у блока `place = {p, k}`, потомки родителя это блоки с `place.p = id`, отсортированные по `(k, blockId)` | массив `children` при одновременных переносах даёт дубликаты и потерянные блоки; одно поле разрешается «последний выигрывает» |
| перенос                    | запись `place` целиком                                                                                                | родитель от одного переноса и позиция от другого не смешиваются                                                               |
| порядок                    | `k` это строка между ключами соседей (дробная индексация) со случайным хвостом                                        | вставка в одно место двумя клиентами не даёт одинаковых ключей; перенумерация не нужна                                        |
| `props`                    | `Y.Map`, ключ на свойство                                                                                             | разные свойства одного блока правятся независимо                                                                              |
| `content`                  | `Y.Text`; атрибуты `InlineNode` это атрибуты форматирования Yjs                                                       | посимвольное слияние текста                                                                                                   |
| формула, ссылка на заметку | как сейчас: один символ `FORMULA_CHAR` с атрибутом (`formula`, позже `noteRef`)                                       | правка формулы это смена атрибута с одним победителем; вставка-объект Yjs при одновременной правке дала бы две формулы        |
| `flavour`                  | строка                                                                                                                | последний выигрывает                                                                                                          |
| удаление блока             | ключ удаляется из `blocks`, потомки тоже                                                                              | удаление выигрывает у одновременной правки внутри блока                                                                       |
| `meta` блока               | не пишется                                                                                                            | время клиента недостоверно; опции `meta` и `collab` вместе это ошибка конфигурации                                            |

`text` создаётся вместе с блоком, а не при первом вводе: иначе два клиента, превратившие разделитель в абзац, создали бы два
текста, и один пропал бы.

### Проекция

Слияние может дать состояние, которое ни одна команда не создала бы. Проекция это чистая функция
`project(ydoc, schema) → DocumentSnapshot`, одинаковая у всех клиентов, поэтому все видят одно и то же:

1. Записи неверной формы пропускаются.
2. `children` строятся из `place`, порядок `(k, blockId)`.
3. Блоки, недостижимые от корня, прикрепляются в конец первого потомка корня (`block:note`) вместе с поддеревьями: сироты
   (родитель удалён, пока в него переносили блок) по своему верхнему блоку, цикл (два одновременных переноса друг в друга) по
   блоку с наименьшим `id`.
4. По схеме: блок, которому `validateRelation` или предел глубины не разрешают лежать в его родителе, поднимается к первому
   предку, где можно, и встаёт сразу после ветки, из которой вышел. `props`, не прошедшие `propsSchema`, заменяются значениями по
   умолчанию.

Правила 1–3 не зависят от схемы: их же реализует сервер, когда собирает снимок, и они закрепляются общими тестовыми данными
(обновление Yjs → ожидаемый снимок). Правило 4 выносится в отдельную функцию `normalizeSnapshot(snapshot, schema)`: её вызывает
мост и любой, кто открывает снимок с сервера через `deserializeDocument`.

Проекция ничего не пишет в `Y.Doc`. Если бы каждый клиент «чинил» цикл записью, клиенты перебивали бы друг друга, а починка
попадала бы в историю отмены. Нарушение исчезает, когда кто-нибудь снова перенесёт блок.

## Подключение

```ts
import * as Y from 'yjs';
import { Editor } from '@inkbrick/engine';
import { createCollab } from '@inkbrick/collab';

const collab = createCollab({ ydoc: new Y.Doc(), schema });

transport.onUpdate((update) => collab.receive(update)); // не Y.applyUpdate: мост придерживает правки на время IME
collab.onLocalUpdate((update) => transport.send(update));
await transport.synced; // получено полное состояние

const editor = new Editor({ schema, document: collab.createDocument(), history: collab.history });
collab.attach(editor);
```

До `transport.synced` редактор не создаётся: приложение показывает снимок в режиме «только чтение» или заглушку. Пустой
`Y.Doc` без `meta` это ошибка: начальный документ создаёт тот, кто создаёт документ (сервер), а не первый открывший клиент,
иначе двое создадут структуру дважды.

## Из хранилища в Yjs

Мост подписан на `store.subscribeChanges`. Слушатель получает `id` изменённых блоков, этого достаточно: мост сравнивает
каждый такой блок в хранилище с его записью в `Y.Doc` и пишет разницу одной транзакцией Yjs с меткой `origin: collab`.

| В хранилище                          | В Yjs                                                                                                                                          |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| блока нет                            | удалить ключ из `blocks`                                                                                                                       |
| блок новый                           | создать запись с `flavour`, `place`, `props`, `text`                                                                                           |
| другой `flavour`                     | записать `flavour`; ключи `props`, которых нет у нового типа, удалить                                                                          |
| другие `props`                       | записать только изменившиеся ключи                                                                                                             |
| другой `content`                     | разница текста (ниже)                                                                                                                          |
| другой порядок `children` у родителя | новые `place` только тем потомкам, которые не входят в самую длинную общую упорядоченную цепочку: при переносе одного блока меняется один ключ |

### Разница текста

`UpdateBlockChange` несёт `content` целиком, а Yjs нужны вставки и удаления. Мост сравнивает новый `content` с текущим `Y.Text`:

1. Общий префикс и суффикс по тексту; середина это одно удаление и одна вставка. При вводе по символу получается ровно одна
   вставка.
2. **Границы не попадают внутрь суррогатной пары.** Yjs заменяет половинки разорванной пары на U+FFFD у той реплики, которая её
   разорвала, и реплики расходятся. Замена 😀 на 😁 без этого правила дала бы общий префикс из половины символа.
3. Вставка всегда передаёт полный набор атрибутов (`text.insert(i, s, attrs)`), даже пустой: без него Yjs наследует атрибуты
   соседа.
4. В совпавших участках сравниваются атрибуты по отрезкам; отличия пишутся `text.format`, снятый атрибут это `null`.
5. Если каретка известна (она есть в `HistoryMeta`), неоднозначность «какая из одинаковых букв вставлена» решается в её пользу.

Результат `Y.Text.toDelta()` перед сравнением нормализуется (`normalizeInlineNodes`): Yjs может вернуть соседние отрезки с
одинаковыми атрибутами отдельно.

Позже команды могут сами сообщать операции (`InlineOp` в модели уже есть), и разница станет запасным путём и проверкой.

## Из Yjs в хранилище

После каждой транзакции Yjs с чужой меткой (обновление снаружи, undo, redo):

1. По событиям Yjs собрать `id` блоков, у которых изменились текст, `props` или `flavour`; если менялись `place` или состав
   `blocks`, пересчитать структуру целиком (это сортировка, для заметки в тысячи блоков доли миллисекунды).
2. Построить проекцию затронутых блоков, сравнить с хранилищем, получить список `Change`.
3. Применить `store.transact(fn, { history: false, origin: 'remote' })`. Слушатель моста пропускает коммиты с этой меткой.

Полное восстановление это тот же код со всеми блоками в списке затронутых. Мост запускает его, если применение бросило
исключение, а в тестах после каждого шага проверяется `editor.serialize()` = `normalizeSnapshot(project(ydoc))`.

## Отмена

`History` откатывает блок целиком (`UpdateBlockChange.revert`) и затёр бы чужие правки того же блока, поэтому в совместном режиме
историю заменяет `Y.UndoManager`: он отменяет только свои операции.

- `collab.history` реализует интерфейс истории (`canUndo`, `canRedo`, `undo`, `redo`, `seal`, `clear`, подписка); `Editor` и
  `useHistory` работают с ним, как с обычной историей.
- Отслеживаются только транзакции с меткой моста. Отмена меняет `Y.Doc`, а в хранилище попадает путём «из Yjs».
- Слияние шагов: `captureTimeout` равен `mergeWindowMs`. `UndoManager` сливает всё подряд в пределах окна, а Inkbrick только
  правки с одинаковым `mergeKey`, поэтому мост вызывает `stopCapturing()`, когда ключ сменился, отсутствует или вызван `sealHistory`.
- Каретка «до» и «после» шага хранится в `stackItem.meta` как относительные позиции Yjs и переводится в `blockId + offset` при
  отмене.

Проверить в прототипе: отмена удаления блока (восстановление вложенных `Y.Map` и `Y.Text`). Если ненадёжно, удаление станет
отметкой `deleted` вместо удаления ключа, и формат изменится.

## Выделение и присутствие

- Выделение Inkbrick это `blockId + offset`; чужая вставка перед кареткой сдвигает смещение. Мост хранит локальное выделение как
  относительные позиции Yjs (обновляет при каждой смене выделения) и после чужой правки возвращает пересчитанное
  `EditorSelection`, которое слой React ставит в DOM.
- Присутствие через `y-protocols/awareness`: `{ user: { id }, selection: { anchor, focus } }`, точки это относительные позиции.
  Имя и цвет приложение берёт по `id` само.
- Отрисовка чужих курсоров это отдельный компонент поверх документа (`<RemoteCursors>`), а не часть `renderInline`: чужой курсор
  не должен перерисовывать текст блока.

## Ввод через IME

Во время композиции слово живёт только в DOM, модель обновляется на `compositionend` (`useEditorInput.ts`). Если в это время
применить чужую правку, произойдёт одно из двух: перерисовка блока сломает композицию, либо разница на `compositionend` будет
посчитана относительно уже изменившегося `Y.Text` и сотрёт чужой текст.

Решение: пока идёт композиция, `collab.receive` складывает входящие обновления в очередь и не применяет их к `Y.Doc`. На
`compositionend` сначала коммитится локальная правка, затем применяется очередь. Композиция длится секунды; если дольше пяти
секунд, очередь применяется принудительно. Редактор для этого сообщает о начале и конце композиции
(`editor.setComposing(blockId | null)`).

## Известные ограничения

| Ситуация                                                                          | Что произойдёт                                                                                                                 |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Один нажал Enter в середине абзаца, другой в это время печатал в его правой части | правая часть уезжает в новый блок как новый текст, одновременный ввод в неё теряется; то же при склейке блоков через Backspace |
| Один удалил блок, другой печатал в нём                                            | удаление выигрывает; автор удаления может вернуть блок через undo                                                              |
| Два человека одновременно удалили последние блоки заметки                         | каждый клиент добавит пустой абзац (`DeleteBlockCommand`), получится два                                                       |
| Оба удалили всё, и абзац никто не добавил                                         | контейнер заметки пуст; редактор должен показать место для ввода и создать абзац при первом вводе, а не при загрузке           |
| Одновременная смена оформления одного фрагмента                                   | до очередной полной сверки с сервером фрагмент может выглядеть по-разному у разных людей (свойство Yjs)                        |
| Хук контроллера блока (`onCreate` и другие) делает правку в ответ на изменение    | при чужом изменении её сделает каждый клиент; хуки получают `origin` и на `remote` не пишут                                    |

## Что меняется в существующих пакетах

| Пакет              | Изменение                                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `store`            | `transact(fn, { origin })`; слушатель `subscribeChanges` получает второй аргумент `{ origin: 'local' \| 'remote' \| 'undo' \| 'redo', mergeKey }` |
| `store`            | история за интерфейсом; `DocumentStoreOptions.history` принимает свою реализацию                                                                  |
| `engine`           | `EditorOptions.history` принимает реализацию истории; `Editor.undo/redo` идут через неё                                                           |
| `engine`           | `BlockControllers` передаёт `origin` в хуки                                                                                                       |
| `engine`           | `editor.setComposing`, подписка на него                                                                                                           |
| `document`         | `normalizeSnapshot(snapshot, schema)` (правило 4 проекции)                                                                                        |
| `react`            | `useEditorInput` сообщает о композиции; чтение и установка выделения в координатах модели доступны мосту; пустой контейнер заметки принимает ввод |
| `react`            | `<RemoteCursors>` и стили `data-inkbrick-remote-*` в `@inkbrick/styles`                                                                           |
| `scripts/size.mjs` | отдельная строка бюджета для `@inkbrick/collab` без Yjs; существующие бюджеты не меняются                                                         |

Все изменения ядра обратно совместимы: без моста поведение прежнее.

## Тесты

- **Фазз-тест сходимости** (Node, без DOM: движок работает без браузера). N редакторов, у каждого мост и свой `Y.Doc`; сеть в
  памяти задерживает, переставляет и на время обрывает доставку. Случайные команды: ввод и удаление текста (с эмодзи и
  формулами), оформление, Enter, Backspace на границе, удаление и перенос блока, Tab и Shift+Tab, смена типа, вставка фрагмента,
  undo и redo. После полной синхронизации: все `Y.Doc` равны; у каждого `editor.serialize()` равен
  `normalizeSnapshot(project(ydoc))`; снимки всех редакторов равны и проходят `validateSnapshot`; в тексте нет U+FFFD.
  Зерно печатается при падении. В CI короткий прогон, длинный по расписанию.
- **Направленные тесты**: цикл из двух переносов, перенос в удаляемый блок, одновременная смена типа и свойства, одновременный
  Enter и ввод, undo при чужих правках в том же блоке, undo удаления блока, вставка между одинаковыми ключами порядка.
- **Общие данные с сервером**: набор «обновление Yjs → снимок» для правил 1–3 проекции.
- **Playwright**: два редактора на одной странице песочницы, IME, курсоры, доступность.

## Прототип (K0)

Пакет `packages/collab`, страница песочницы с двумя редакторами и сетью в памяти (с ползунком задержки и кнопкой «обрыв»).
Объём: формат, оба направления, отмена, выделение, придерживание на время IME, фазз-тест. Без сервера, без курсоров.

Готово, когда фазз-тест стабильно зелёный, а перенос блоков, undo и IME не ломаются в ручной проверке. По итогам решается:
остаётся ли удаление блока удалением ключа; хватает ли разницы текста или командам нужно сообщать операции; укладывается ли
пересчёт структуры во время на больших документах. До этого формат `inkbrick-yjs` не замораживается.

## Не проверено

Всё выше это проект по чтению кода Inkbrick и документации Yjs. Запускалась только проверка формата на «голом» Yjs (без моста):
три реплики со случайными правками сходятся; оттуда правило про суррогатные пары, нормализация `toDelta` и наблюдение про
оформление, зависящее от порядка доставки.
